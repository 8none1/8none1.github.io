# Rebuild plan: whizzy.org (8none1.github.io)

Handoff instructions for another Claude instance. Goal: replace the ageing
beautiful-jekyll / WordPress-import site with a clean, lightweight static site
that deploys reliably via **GitHub Actions**, keeping all real content and URLs.

## Why we're doing this
The current site is a beautiful-jekyll WordPress import pinned to the old
GitHub-Pages Jekyll 3.x. It's ~56 MB tracked (+73 MB git history), pulls a
`remote_theme` on every build, and carries cruft (a 14 MB static-export zip,
staticman, etc.). Deploys via the classic "deploy from branch"
`pages-build-deployment` have become flaky ("Deployment failed, try again later"
/ queue timeouts), especially under frequent pushes. A clean rebuild + an
Actions-based deploy fixes reliability and maintainability.

## HARD CONSTRAINTS (do not break these)
1. **Custom domain**: keep `CNAME` = `www.whizzy.org`. The site is served at
   https://www.whizzy.org.
2. **Post permalinks**: current scheme is `permalink: /:year-:month-:day-:title/`
   (e.g. `/2026-06-14-growatt-shinewifi-x-esphome-modbus-bridge/`). Preserve it
   exactly, external links and SEO depend on it. 70 posts in `_posts/`.
3. **The `flights/` directory is sacred.** It holds self-contained CesiumJS
   flight-replay pages (`*.html`) plus `flights/models/*.glb` and
   `flights/index.html`, served at `www.whizzy.org/flights/...`. These are
   generated by a SEPARATE project (`ognflights`, repo `8none1/ognflights`) and
   pushed here by its "Publish to whizzy.org" GitHub Action via a deploy key.
   - Must be served **verbatim** (they are complete HTML; do NOT run them through
     the site's templating/markdown). Keep the exact paths.
   - The rebuild must not delete or rename anything under `flights/`.
4. **Keep the ognflights publish integration working.** That action clones this
   repo, copies files into `flights/`, commits and pushes to the default branch.
   After the rebuild, a push to the default branch must still trigger the new
   deploy workflow and publish `flights/` unchanged. (No change needed in the
   ognflights repo, but verify the flow end-to-end after cutover. The deploy key
   named `ognflights-publish` on this repo must remain valid.)
5. **Deploy must be GitHub Actions-based** (Pages "Source" = GitHub Actions), not
   the classic branch deploy. This is the core reliability fix.

## What to KEEP (real content)
- `_posts/` — 70 markdown posts (dates 2011–2026). Body content + titles.
- Pages: `aboutme.md`, `will-cooke.md` (personal pages). Review `index.html`,
  `categories.html`, `tags.html`, `404.html` — rebuild equivalents.
- Images actually referenced by posts/pages (see "Trim images" below).
- `favicon.ico` / `favicon.png`, `robots.txt`, `CNAME`.
- RSS feed (nice for subscribers) — regenerate with the new generator.
- Tags/categories index if still wanted (optional).

## What to DROP (cruft — safe to delete)
- `wp-content/uploads/2017/03/wp-static-html-output-1-1490456400-will.zip` (14 MB junk).
- `staticman.yml`, `beautiful-jekyll-theme.gemspec`, the committed `_site/`
  (should be gitignored anyway), `Gemfile.lock` if switching off Jekyll.
- `.github/workflows/ci.yml` (the disabled beautiful-jekyll docker CI).
- Any `wp-content` media not referenced by kept content (see below).
- The remote_theme dependency and beautiful-jekyll `_layouts`/`_includes`
  (replace with a minimal own theme).

## Generator choice (confirm with Will first)
The reliability win comes from the Actions deploy, which works with ANY generator.
Pick based on migration effort vs lightness:

- **Option A — Jekyll 4.x, minimal, built via Actions (RECOMMENDED, lowest risk).**
  Posts, kramdown, front-matter and the permalink scheme migrate with ~zero
  changes. Drop `remote_theme`; hand-roll 3–4 tiny layouts (default/post/page)
  and minimal CSS. Build with `actions/jekyll-build-pages` or `bundle exec jekyll
  build` in the deploy workflow. Keeps Ruby, but pinned and reliable.
- **Option B — Hugo (lightest/fastest).** Single binary, superb in CI, built-in
  RSS/taxonomies. Cost: mechanical migration of 70 posts' front matter (Jekyll →
  Hugo), permalink config (`permalinks` in `hugo.toml` to match the scheme),
  kramdown→Goldmark nuances, and any Liquid in posts → shortcodes.
- **Option C — Eleventy (11ty).** Lightweight JS; more assembly for blog features.

Recommendation: **A** unless Will wants maximum lightness, then **B**. Whatever is
chosen, the `flights/` tree must be a pure passthrough (Jekyll: files without
front matter pass through, but confirm; Hugo: put under `static/`; 11ty: add
passthrough copy).

## Step-by-step
1. **Branch, don't cut over live yet.** Work on a `rebuild` branch. The live site
   keeps serving from the current setup until the new one is verified.
2. **Confirm generator** (above) with Will.
3. **Inventory images**: grep posts/pages for referenced image paths; copy only
   those into the new structure (e.g. `assets/img/…`), rewriting paths if needed.
   Target: get the repo from ~56 MB down to a few MB.
4. **Migrate posts**: move `_posts/*.md` into the new layout; keep dates/titles;
   preserve the permalink scheme so URLs are identical. Spot-check a handful of
   posts render (code blocks, images, links).
5. **Rebuild the shell**: minimal home page (post list), a post layout, a page
   layout, 404, favicon, RSS, optional tags/categories. Keep it clean and legible;
   this is a personal blog, not a magazine.
6. **Preserve `flights/`** untouched as a passthrough; verify a replay page still
   loads and `flights/models/*.glb` resolve.
7. **Add the deploy workflow** (`.github/workflows/deploy.yml`): build the site and
   deploy with `actions/upload-pages-artifact` + `actions/deploy-pages`, triggered
   on push to the default branch + `workflow_dispatch`. Set repo **Pages → Source
   = GitHub Actions**. Add `concurrency: {group: pages, cancel-in-progress: false}`.
8. **Keep `CNAME`** in the published output (put it in the source so it lands in
   the build output, or add it via the workflow).
9. **Test** (see below) on the branch using a preview/build before cutover.
10. **Cut over**: merge to default branch, flip Pages source to Actions, confirm
    live. Keep the old config in git history for rollback.

## Testing / verification
- Build locally (or in CI) and confirm: home lists posts; 3–5 posts render with
  images/code; permalinks match old URLs exactly; RSS validates; 404 works.
- **Critical**: confirm `flights/` pages are copied verbatim and load. A headless
  check is available: `google-chrome --headless=new --enable-unsafe-swiftshader
  --virtual-time-budget=20000 --screenshot=out.png <url>` renders a Cesium page;
  capture stderr for JS errors. (The ognflights repo used this to verify replays.)
- After cutover, do a real end-to-end test of the ognflights publish action:
  trigger it and confirm it still publishes into `flights/` and the site
  redeploys via the new workflow.

## Rollback
Everything stays in git history. If the new deploy misbehaves, revert the merge
and flip Pages Source back to "Deploy from branch". Keep the current `_config.yml`
and layouts recoverable until the new site has been stable for a few days.

## Optional (advanced)
- **Shrink git history** (the 73 MB `.git`, mostly the 14 MB zip + old media +
  our repeated large `flights/*.html` regenerations) with `git filter-repo`.
  Rewrites history — do only with Will's explicit OK, and force-push carefully.
- Consider serving the big `flights/*.html` more efficiently later (they're ~4 MB;
  fine for now).

## Decisions (confirmed with Will, 2026-07-03)
1. **Generator: Jekyll 4.x, KEEPING the existing beautiful-jekyll look.** Will
   wants the current visual style, brand graphics and logos preserved exactly.
   The theme is ALREADY vendored locally (`_layouts`, `_includes`,
   `assets/css/beautifuljekyll.css` + `custom-styles.css` with dark-mode +
   author-box, and all brand images in `assets/img/`). So do NOT hand-roll a new
   theme. Instead: drop `remote_theme` + `jekyll-remote-theme` (the local copy
   already overrides it and renders the site), pin Jekyll 4.x, and rely on the
   vendored files. Result should be visually byte-identical. If the local copy is
   missing anything vs remote 6.0.1, copy that file down locally rather than
   restyle. Prune only unwired includes (disqus, staticman, matomo, gtm, giscus,
   fb-comment, utterances) and the stray empty `_includes/social-` file — none
   are visual. Verify pixel-parity with a headless screenshot before cutover.
2. **Keep BOTH tags and categories** as simple static index pages (preserve any
   existing links).
3. **Git history: rewrite LATER, as a separate step.** Ship the new Actions-based
   site first; once stable, do a deliberate `git filter-repo` rewrite +
   force-push with Will's explicit OK, coordinated around ognflights publish
   timing. Do NOT fold the rewrite into the initial rebuild.
4. **Keep all 70 posts.** No content pruning.
